# Vitest, Testing Library and TDD

Date: 2026-11-07 · Status: accepted

## Context

The suite ran on Jest through `next/jest` (`2026-11-06-tests-jest-tdd.md`). `next/jest` loads `.env` by
itself: a test once passed locally and failed in CI, which has no `.env`. The author wants Vitest.

## Decision

Still in force from the superseded record:

- Testing Library in jsdom; work is test-driven (a failing test committed on its own as `test:`, then the
  code, then the refactor); tests are written to the maximum and coverage only grows.
- Tests sit next to the module they cover; shared mocks and helpers live in `tests/mocks` and
  `tests/utils`.
- End-to-end tests stay rejected (`2026-11-06-no-e2e-tests.md`): Vitest + Testing Library only.

Changed:

- The runner is Vitest (`vitest run`, `vitest` for watch) with `jsdom`, `clearMocks` and `restoreMocks`.
- Every test file imports `describe`, `test`, `expect`, `vi` and the rest from `'vitest'`; there are no
  globals. A setup file (`tests/setup`) runs Testing Library's `cleanup` after each test, because it
  cannot register itself without a global `afterEach`.
- Vitest does not read `.env`, so a test never depends on it.
- `server-only` and `@/` are Vite aliases in `vitest.config.js`; JSX needs no React plugin.
- Rejected: staying on Jest (`next/jest` and its automatic `.env`); `globals: true` (implicit names hide
  where a helper comes from).

## Consequences

- A new test file starts with its Vitest imports; a mock factory reads variables through `vi.hoisted`
  (`ai/rules/testing.md`).
- Another runner needs the author's explicit ask and a new record.
